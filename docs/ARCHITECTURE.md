# PhotoSheet architecture

This document describes the current application boundaries. It is a contributor guide, not a promise of a stable library API.

## Runtime layers

~~~text
React + TypeScript UI
        │ Wails bindings
        ▼
Go application service
        │
        ├── scanner       file discovery, image metadata and hashes
        ├── packing       deterministic MaxRects placement
        ├── renderer      memory/tile canvas and PNG/JPEG/TIFF output
        ├── project       project.json validation and migration
        ├── resolver      processed-sheet candidate matching
        ├── extractor     crop, orientation, naming and output validation
        └── raw           DNG probe, fallback decode and optional native boundary
~~~

The CLI in cmd/photosheet and the Wails entry point in cmd/photosheet-gui call the same internal/app.Service. The frontend owns interaction, progress display and layout preview; it does not implement image packing or extraction.

## App shell

The GUI is compiled only with the wails build tag. Wails embeds the generated frontend assets from cmd/photosheet-gui/frontend/dist; that directory is generated by frontend/scripts/sync-wails-frontend.mjs and is intentionally ignored by Git. The source frontend remains in frontend/.

The GUI stores recent processed locations in the platform user configuration directory. Those locations never enter project.json.

## Project schema

internal/model owns the serializable model and validation rules. internal/project handles atomic JSON writes, sidecar metadata and in-memory migration from schema versions 1 and 2 to version 3. Unknown JSON fields are ignored for forward compatibility. A project file is data only; it is never executed.

See PROJECT_FORMAT.md for field and coordinate details.

## Pack path

1. scanner expands files/directories, rejects unsupported or unsafe inputs, and probes dimensions, orientation, bit depth and ICC metadata.
2. packing groups compatible color profiles in Strict Lossless mode and chooses a deterministic MaxRects result.
3. renderer writes a PNG/TIFF/JPEG sheet. 16-bit PNG/TIFF uses the high-depth and tile-backed paths when the memory budget requires it.
4. project writes the project atomically after the sheet metadata is known.

The source image is opened read-only. RAW files are probed during scanning and decoded only when the renderer needs pixels.

## Restore path

1. resolver scans user-selected processed files/directories and validates their real image format.
2. It matches stable sheet identity, canonical stem, explicit processed suffixes, dimensions and optional manual bindings.
3. Ambiguous, missing, corrupt and unsafe-transform candidates remain visible instead of being guessed.
4. extractor reads only contentRect, reverses the packing rotation, applies the display orientation convention and writes a collision-safe output name.

## RAW pipeline boundary

internal/raw exposes a small RawBackend interface. The public fallback parses TIFF/DNG metadata and decodes only its supported uncompressed/Deflate subset. Native LibRaw/DNG SDK integration is isolated behind build tags and a narrow C ABI. It is not required for a core build.

See RAW_PIPELINE.md and RAW_BACKEND.md.

## Updater

internal/updater fetches a manifest, verifies its Ed25519 signature, streams the package while checking size and SHA-256, and delegates replacement to cmd/photosheet-updater. The helper backs up the current executable and restores it if replacement fails. Update URLs and signing keys are deployment configuration, not repository secrets.
